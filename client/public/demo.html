What you're watching

  1. An outside agent works through Aftercare's MCP gateway.It holds a scoped Aftercare key, never your app tokens. Aftercare makes each call inside one repository, team and channel, and records the values before and after.
  2. The agent fails the way real agents do.A lost response makes it create a duplicate GitHub issue, a stale roster clears the Linear owner, and it announces success in Slack. Aftercare checks the run against the apps and flags all three.
  3. A bounded AI investigator proposes a repair.It reads the run and the live records with read-only tools, picks from a few safe actions per record, and deterministic policy checks every choice. Each change cites its evidence.
  4. A person keeps working, and Aftercare notices.A simulated teammate adds work to the duplicate issue. Approval is tied to the exact app state, so the old plan is blocked, and the new plan keeps the issue open.
  5. The repair itself is interrupted.The connection drops right after the first write lands. On resume, Aftercare reads the app first, sees the write happened, and finishes without repeating it.
  6. The outcome is verified in the real apps.The added work survives, the owner is restored, Slack gets exactly one correction, and everything is exported as a receipt.

What makes it safe

Bring your own agentMCP gateway or Recorder API; scoped, revocable keys, and every reported action checked against the apps.
Live monitor & alertsWatch actions as they happen; a Slack alert links to the repair when a run goes wrong.
AI that can't writeRead-only tools, a strict budget, a fixed action list, and escalation when evidence conflicts.
Approval bound to realityA person approves one exact plan against one exact app state; any change makes it stale.
Rechecks, journal, read-backEvery write is rechecked first, journaled, and verified afterwards, so interruptions never cause duplicates.
Built to generalizeIncidents are definitions over one engine; a second incident type was added without engine changes.
